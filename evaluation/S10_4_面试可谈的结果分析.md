这个实验的意义不是证明 Query Rewrite 一定有效，而是验证它到底有没有用。
现在得到的是一个明确结论：
当前 Query Rewrite + Multi-query RRF 不值得启用。
证据是：
指标	S09 RRF	S10 多查询	结论
通过数	45	45	没提升
Recall@4	0.9815	0.9815	没提升
Hit@1	0.9762	0.9524	变差
MRR	0.9881	0.9762	变差
延迟	23.99 ms	82.59 ms	增加 3.4 倍
E33	失败	失败	没解决


所以最终决定可以是：
保留 Query Rewrite 代码作为实验能力
但生产路径暂时关闭 Multi-query
最终排序继续使用 S09 RRF
为什么必须做这个实验
因为“Query Rewrite 可能提升召回”只是假设，不是事实。
如果不做，你无法回答：
- 改写是否真的找到新资料；
- 多查询是否只是重复原查询；
- 关键词查询是否增加噪声；
- 原问题排名是否被稀释；
- 延迟是否值得；
- E33 是查询表达问题，还是排序问题。
现在可以明确回答：
E33 不是主要因为问题表达不好。
因为：
原始 vector：知识手册第 9 页排第 5
多查询 RRF：知识手册第 9 页仍排第 5
Query Rewrite 后排名没有变化，说明主要瓶颈不是 Query 表达，而是：
候选排序
来源多样性
同一文档多个 child 霸榜
这个实验排除了一条路线
如果没有这个实验，你可能会一直误以为：
再加一种查询就会变好
现在证据表明：
简单地增加 semantic 和 keyword 查询
并给三者同权重
反而降低质量
这能避免把 Multi-query 错误上线。
它还提供了工程基础设施
后续仍然可以复用：
S10_2 改写缓存
original/semantic/keyword 三种 query
多查询召回接口
全局 RRF 融合
改写耗时统计
fallback
只是当前的融合配置暂时没有效果。
面试时这类结论反而很有价值
可以这样回答：
我在 46 条评测集上实现了 Query Rewrite + Multi-query RRF。
原始 S09 RRF 的 Hit@1 是 0.9762、MRR 是 0.9881。
多查询后通过数仍为 45，但 Hit@1 降到 0.9524，MRR 降到 0.9762，延迟从约 24ms 增到约 83ms，因此没有启用。
分析发现语义改写和原问题高度相似，关键词查询引入 BM25 噪声，三路等权融合稀释了原始向量结果。
下一步不再盲目加查询，而是转向 parent-aware 去重或 rerank。

这比简单说“我加了 Query Rewrite”更有工程判断力。
这不代表 Query Rewrite 永久没用
只代表当前实现方式不行：
三路等权
原始 + 语义 + 关键词都占同样权重
可以继续试验：
original 权重高，semantic/keyword 只做补充
只在原始查询结果不足时触发改写
对改写结果设置更严格阈值
按 query type 分层融合
使用 rerank 处理多查询候选
但这些要等 S10-5 对比和后续 S12 Rerank。
所以当前结论不是：
Query Rewrite 没用
而是：
这次 Query Rewrite 的实现和参数没有带来收益，
因此不应直接进入生产路径。
这正是评测的意义：防止你凭感觉把无效复杂度加进系统。
