## 一句话定位

这套代码 = **给所有工具调用套的「自动容错防护罩」**

你之前写的 `ToolCallRepository` 是「记录工具调用的账本」，`Checkpointer` 是「任务存档读档」，而这套 resilience 执行器，是专门解决「工具调用失败了、卡住了怎么办」的问题，是生产环境的「稳定性保险」。

## 一、先想：没它的时候，你会有多痛苦？

你之前写工具调用（比如 `shell.run`、调用第三方 API），大概率会遇到这些问题：

1. **卡死**：调用 shell 命令 / 第三方接口，有时候网络波动、下游卡住，函数半天不返回，整个任务直接挂死在这，后面的步骤都走不了。
2. **偶发失败**：网络闪断一下、下游瞬时过载，调用失败了。其实重试一次大概率能成，但代码没写重试，任务直接宣告失败，非常可惜。
3. **重试风暴**：如果下游崩了，所有任务同时失败、同时重试，每秒成百上千次请求打过去，本来下游只是卡一下，直接被打瘫痪。
4. **无效重试**：有的错误（比如参数写错了、权限不够），重试多少次都不会成功，但代码无脑重试，浪费时间和资源。
5. **写法混乱**：每个工具调用各写各的重试逻辑，有人重试 2 次有人重试 5 次，有人固定间隔有人乱等，维护起来一团糟。

这套执行器，就是把这些问题一次性、统一地解决掉。

## 二、到底怎么用？套到你的工具调用里就懂了

我用你最熟悉的「shell 工具调用」举一个完整例子，你马上就知道怎么嵌到你的系统里。

### 第 1 步：先有配置文件（对应 S17-1）

```
{
  "operations": {
    "shell.run": {
      "timeout": { "timeout_ms": 30000 },
      "retry": {
        "max_attempts": 3,
        "base_delay_ms": 200,
        "max_delay_ms": 2000,
        "jitter_ratio": 0.5
      }
    }
  }
}
```

### 第 2 步：加载配置，拿到策略

```
config = load_resilience_config(Path("resilience.json"))
shell_policy = config.operations["shell.run"]
```

### 第 3 步：用执行器包裹你的真实业务函数

这是最核心的用法：**你只负责写真正的业务逻辑，超时、重试、退避、错误分类，全交给执行器**。

```
# 这是你原本的业务函数：真正执行 shell 命令
def real_shell_exec(command: str) -> dict:
    # 这里是调用系统 shell 的真实逻辑
    return {"exit_code": 0, "output": "xxx"}

# 这是用执行器包裹后的调用
def call_shell_with_resilience(run_id: str, tool_call_id: str, command: str) -> ExecutionResult:
    # 1. 用 lambda 把参数绑好，变成无参函数
    business_func = lambda: real_shell_exec(command)
    
    # 2. 丢给执行器，它自动帮你做超时+重试
    result = execute_with_policy(
        operation_name="shell.run",
        timeout_policy=shell_policy.timeout,
        retry_policy=shell_policy.retry,
        func=business_func,
    )
    
    # 3. 成功后自动更新工具调用记录（和你之前的仓储联动）
    tool_repo.mark_succeeded(run_id, tool_call_id, result.value)
    return result
```

### 实际运行时，它内部自动做了这些事：

1. 开始计时，把 `real_shell_exec` 丢到子线程运行
2. 30 秒内成功 → 直接返回结果
3. 30 秒没返回 → 自动中断，抛出超时异常
4. 如果失败了，判断是不是可重试的错误（超时、连接错误）
   - 不可重试（比如参数错误）→ 直接抛错，不浪费时间
   - 可重试 → 等 200ms（加随机抖动），再来第二次
5. 第二次又失败 → 等 400ms，再来第三次
6. 第三次还失败 → 抛出「重试耗尽」异常，上层可以接走去走 fallback 兜底

全程你不用写一个循环、一个 `sleep`、一个超时判断。

## 三、这么写有什么用？核心价值

### 1. 业务代码只关心业务

所有容错逻辑全抽走了，写工具调用的时候不用再想「超时怎么办、失败要不要重试」，专注写业务逻辑就行。

### 2. 全系统统一容错标准

所有工具都用同一套配置、同一套执行逻辑，不会出现有的重试 3 次、有的重试 5 次的混乱情况。要改全局策略，改配置文件就行。

### 3. 保护下游系统

指数退避 + 随机抖动，保证下游故障时，重试流量是平滑散开的，不会形成重试风暴把下游打崩。这是生产环境和玩具代码的核心区别。

### 4. 错误语义清晰，上层好对接

三种自定义异常（超时、不可重试、重试耗尽），上层的熔断、降级、限流组件可以精准捕获处理。
比如捕获到重试耗尽，就自动走 fallback 兜底；捕获到大量超时，就触发熔断。

### 5. 天然可观测

每次执行都返回「尝试次数、总耗时」，很容易就能统计每个工具的：

- 成功率、失败率
- 超时率
- 平均重试次数
- 平均耗时

不用额外埋点，直接就能做监控告警。

## 四、它在你整套系统里的位置

```
工作流引擎
    ↓
【弹性执行器层】← 你现在写的就是这层
    ↓ （自动做超时、重试、熔断、限流、幂等）
真实工具调用（shell、API、数据库）
    ↓
ToolCallRepository 记录执行结果
    ↓
Checkpointer 保存状态快照
```

它是夹在「业务逻辑」和「真实工具」之间的一层透明代理。业务代码感觉不到它的存在，但它默默把所有稳定性问题都处理了。

## 最后一句话总结

- **是什么**：通用函数容错执行器
- **怎么用**：传操作名 + 策略 + 业务函数，等着拿结果
- **为什么**：解决 IO 场景的卡死、偶发失败、重试风暴问题，统一标准，提升稳定性
- **用在哪**：所有外部调用、慢调用、容易失败的地方
